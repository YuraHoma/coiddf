# Переклад сайту українською → англійською

Англійська версія сайту збирається з того самого українського контенту, що й
українська. Переклади зберігаються в **`catalog.json`** — це єдине джерело
правди, воно в git.

Головні правила конвеєра:

1. Переклад привʼязаний до **місця в контенті** (`data/home.hero.headline`), а
   не до українського тексту. Клієнт може виправити одруківку в CMS — переклад
   не загубиться.
2. Кожен запис має **статус**: машинний (`machine`) чи вичитаний людиною
   (`human`). **Вичитане людиною скрипт не перезаписує ніколи.**
3. Разом із перекладом зберігається **джерело, з якого його зробили**. Якщо
   український текст потім змінили, запис автоматично стає «застарілим» і
   потрапляє перекладачу на перегляд — мовчки він не зникає.
4. **У CI збірка падає**, якщо на англійську сторінку поїхав би
   неперекладений або застарілий текст.

## Для перекладача

### Крок 1. Отримати файл

Розробник виконує:

```bash
npm run i18n:export          # звичайний CSV (Google Sheets, LibreOffice)
npm run i18n:export:excel    # роздільник ";" — для Excel в українській локалі
```

Зʼявиться файл `scripts/i18n/translations.csv`. За замовчуванням у ньому лише
те, що **потребує уваги**. Щоб вивантажити весь контент разом із уже готовим:

```bash
npm run i18n:export -- --all
```

### Крок 2. Вичитати

Файл відкривається у Excel і в Google Sheets (кирилиця не ламається).
Стовпці:

| Стовпець      | Що це                                                        |
| ------------- | ------------------------------------------------------------ |
| `key`         | службова адреса тексту на сайті. **Не редагувати.**           |
| `status`      | стан запису. **Не редагувати.**                              |
| `source_uk`   | український оригінал — те, що треба перекласти.               |
| `previous_uk` | попередній український текст, з якого робився наявний переклад. Заповнений, лише коли оригінал змінили — порівняйте зі `source_uk`, щоб побачити правку. |
| `english`     | **редагувати тут** — англійський текст.                       |
| `approved`    | **поставити `так`**, коли англійський текст вичитано.         |
| `note`        | коментар перекладача (необовʼязково).                         |
| `source_hash` | службове. **Не редагувати.**                                  |

Значення в `status`:

- `машинний переклад, не вичитано` — переклала машина, потрібна вичитка;
- `джерело змінилось після вичитки` — ви вже перекладали це, але український
  текст потім змінили. Дивіться `previous_uk` проти `source_uk`;
- `джерело змінилось після машинного перекладу` — те саме, але вичитки ще не було;
- `перекладу НЕМАЄ` — новий текст, англійського варіанту ще немає;
- `вичитано людиною` — готове (видно лише з `--all`).

Що робити з рядком:

- переклад правильний → поставте `так` у `approved`;
- переклад треба виправити → перепишіть `english` і поставте `так`.

> Якщо ви змінили `english`, але забули поставити `так` — правку все одно буде
> збережено як людську. Робота не губиться.

Файл зберігати у форматі **CSV (UTF-8)**.

### Крок 3. Повернути файл

Перекладач віддає CSV розробнику, той виконує:

```bash
npm run i18n:import                    # зі scripts/i18n/translations.csv
npm run i18n:import -- шлях/до/file.csv # або з довільного шляху
npm run i18n:import -- --dry-run        # спершу подивитись, що зміниться
```

Імпорт пропускає рядки, чий український оригінал змінився вже після
вивантаження файлу (щоб не записати переклад не того тексту), і повідомляє
про них — такі рядки треба вивантажити й вичитати наново.

## Для розробника

### Команди

| Команда                   | Що робить                                                  |
| ------------------------- | ---------------------------------------------------------- |
| `npm run i18n:check`      | звіт про стан перекладу; у CI — ненульовий код виходу       |
| `npm run i18n:translate`  | машинний переклад нового й зміненого; вичитане не чіпає     |
| `npm run i18n:export`     | CSV для перекладача                                         |
| `npm run i18n:import`     | вичитаний CSV назад у каталог                               |
| `npm run i18n:migrate`    | одноразова міграція старого `cache.json` (вже виконана)     |

Типовий цикл після появи нового контенту:

```bash
npm run i18n:translate   # машина закриває нове, щоб сайт не падав
npm run i18n:export      # віддати перекладачу
npm run i18n:import      # повернути вичитане
npm run i18n:check       # переконатися, що чисто
```

`npm run i18n:translate` ходить у мережу (Google Translate). **Збірка сайту в
мережу не ходить** — `src/_data/en.js` лише читає `catalog.json`.

### Суворість збірки

Двома змінними середовища:

- `I18N_STRICT` — `1` вмикає суворий режим (помилка замість попередження),
  `0` вимикає. **Якщо не задано — суворий режим автоматично вмикається в CI**
  (за наявності змінної `CI`), а локально лишається мʼяким.
- `I18N_REQUIRE` — що саме вважати проблемою:
  - `translated` (типово) — падати на відсутньому й застарілому перекладі;
  - `human` — падати ще й на машинному, не вичитаному людиною.

```bash
I18N_STRICT=1 npm run build                    # відтворити поведінку CI локально
I18N_REQUIRE=human npm run i18n:check          # скільки ще лишилось вичитати
```

> **Коли перекладач закінчить перший повний прохід**, у
> `.github/workflows/deploy.yml` до кроку `npm run build` треба додати
> `env: I18N_REQUIRE: human`. Відтоді жоден невичитаний машинний рядок не
> потрапить на прод. Зараз цей рівень увімкнути не можна — вичитано 0 з 272,
> і деплой би просто зупинився.

### Що де лежить

| Файл             | Призначення                                                     |
| ---------------- | --------------------------------------------------------------- |
| `catalog.json`   | **джерело правди**: переклади, статуси, джерела, хеші            |
| `content.js`     | перелік того, що взагалі перекладається (спільний для збірки й скриптів) |
| `catalog.js`     | правила: статуси, хеші, виявлення застарілого, рівні суворості   |
| `lib.js`         | обхід структури даних і побудова ключів                          |
| `csv.js`         | читання/запис CSV (Excel-сумісний)                               |
| `cache.json`     | **архів** старого формату. Не використовується збіркою. Лишений як страховка після міграції; можна видалити, коли перший прохід вичитки завершиться. |

### Чому не i18next

Клієнт пропонував [i18next](https://github.com/i18next/i18next). Він тут не
підходить, і ось чому:

- i18next вирішує задачу **UI-рядків із наперед заданими ключами**
  (`nav.about`). У нас же переважає **проза, яку клієнт редагує в CMS**.
  Перевести її на ключі означає змусити клієнта правити текст у файлі з
  ключами замість зручного редактора — для нього це гірше, ніж зараз.
- Жодної з чотирьох потрібних нам властивостей — статус «машинний/вичитаний»,
  виявлення зміни джерела, обмін файлами з перекладачем, падіння збірки на
  неперекладеному — **ядро i18next не має**. Усе це є в їхньому платному
  сервісі Locize, тобто підключення i18next не закрило б задачу, а лише додало
  б залежність.
- i18next — рантайм-бібліотека для застосунків. Сайт статичний: уся
  локалізація має статися під час збірки, у браузер зайвий JS везти нема сенсу.

Тому статуси й модель «джерело + його хеш + стан» узято з підходу, що є
галузевим стандартом для перекладацьких файлів (XLIFF `state`), але реалізовано
мінімальним власним кодом без залежностей.
